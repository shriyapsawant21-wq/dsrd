# Distributed Startup Race Debugger - Overall Plan

## Hackathon Context

This project is for GDG DevJams'26.

The idea is to build a local debugger for Docker Compose applications that actively searches for startup race conditions. Instead of only showing container health, the tool explores different startup and readiness timings, finds a failing schedule, minimizes it, and gives a replay command that reproduces the same failure.

## Core Problem

Multi-service applications can fail during startup even when every individual service is correctly configured. A container being started does not mean the application inside it is ready. Databases may still be recovering, migrations may be running, caches may be warming, and endpoints may exist before a service begins listening.

These failures are hard to reproduce because each restart may produce a different timing order. Health checks and dependency declarations help, but they do not reveal hidden timing assumptions inside the application.

## MVP Goal

Build a three-day MVP that can:

1. Run one Docker Compose application repeatedly.
2. Inject controlled startup and readiness delays.
3. Observe container start, service readiness, and failure events.
4. Automatically find at least one failing startup schedule.
5. Minimize the failing schedule into a simple reproducible race.
6. Output a timeline explaining the failure.
7. Provide a replay command for the failing schedule.

## Demo Goal

The final demo should show:

1. A four-service Docker Compose stack normally starts successfully.
2. The debugger runs multiple startup schedules.
3. The debugger discovers a failing ordering.
4. The debugger displays a timeline:
   - service/container start
   - actual readiness
   - first cross-service request
   - failure window
5. The debugger generates a replay command.
6. Running the replay command reproduces the same failure.

## Proposed Tech Stack

### Core Language

- Node.js with TypeScript

Reason:
- Fast to build a CLI.
- Easy JSON handling.
- Good process control for Docker commands.
- Works well with web-based UI agents later.

### CLI

- Node.js
- TypeScript
- Commander.js or Yargs for CLI commands

CLI commands:

```bash
race-debugger search
race-debugger replay failure.json
race-debugger inspect docker-compose.yml
```

### Docker Control

- Docker
- Docker Compose
- Docker CLI through child processes

Core commands:

```bash
docker compose up
docker compose down
docker compose logs
docker inspect
```

### Config and Data Format

- YAML parsing for `docker-compose.yml`
- JSON for schedules, results, and timeline events

Suggested packages:

- `yaml`
- `zod` for validating schedule/result contracts

### Readiness Checks

- HTTP readiness checks using `fetch`
- TCP readiness checks using Node's `net` module
- Optional log scanning through `docker compose logs`

### Demo Stack

Suggested services:

- `api`: Node.js Express service
- `postgres`: PostgreSQL database
- `worker`: Node.js worker that calls the API or database early
- `frontend` or `cache`: simple React/Vite frontend or Redis cache

Recommended demo race:

- API starts immediately.
- API tries to connect to Postgres once on startup.
- Postgres container is running but not ready.
- API fails if Postgres readiness is delayed beyond a threshold.
- The debugger discovers and replays that failing timing.

### UI Agent Interface

The UI agent should consume JSON files generated by the engine:

```json
{
  "status": "fail",
  "failingSchedule": {
    "postgres": {
      "readinessDelayMs": 1800
    },
    "api": {
      "startDelayMs": 0
    },
    "worker": {
      "startDelayMs": 300
    }
  },
  "events": [
    {
      "timeMs": 0,
      "service": "api",
      "event": "container_started"
    },
    {
      "timeMs": 420,
      "service": "api",
      "event": "db_connection_failed"
    },
    {
      "timeMs": 1800,
      "service": "postgres",
      "event": "ready"
    }
  ]
}
```

## Shared Contracts

### Schedule

```ts
type Schedule = {
  id: string;
  services: {
    [serviceName: string]: {
      startDelayMs?: number;
      readinessDelayMs?: number;
    };
  };
};
```

### Timeline Event

```ts
type TimelineEvent = {
  timeMs: number;
  service: string;
  event: string;
  detail?: string;
};
```

### Run Result

```ts
type RunResult = {
  scheduleId: string;
  status: "pass" | "fail";
  events: TimelineEvent[];
  logs: string[];
  failureReason?: string;
};
```

## Success Criteria

The MVP is successful if it can:

1. Run the demo stack normally and show it passing.
2. Run the debugger and discover a failing timing schedule.
3. Explain the failure using a timeline.
4. Replay the exact failure using a saved schedule.
